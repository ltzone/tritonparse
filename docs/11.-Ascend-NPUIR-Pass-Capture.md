# Ascend NPUIR Pass-Level IR Capture

TritonParse can capture the **bishengir NPUIR transformation passes** that run
inside the `bishengir-compile` subprocess during Ascend NPU lowering. This turns
what used to be a black box between `TTAdapter` and `NPUBIN` into a list of
selectable IR stages, one per compiler pass.

```
TTIR (10) → TTAdapter (20) → MLIRBC (30) → BCMLIR (40)
                                              ↓ bishengir-compile subprocess
                              ├─ 401 NPUIR Pass: Canonicalize Module
                              ├─ 402 NPUIR Pass: Convert Linalg to HFusion
                              ├─ 403 NPUIR Pass: Convert HFusion to HIVM
                              ├─ …  (100+ passes, one stage each)
                                              ↓
                                          NPUBIN (10000) → JSON (20000)
```

This is an **opt-in** feature: the dump is large and adds compilation overhead,
so it is off unless you ask for it.

## 🚀 Quick Start

Requires only TritonParse itself plus a working `bishengir-compile` on `PATH`.
Any `triton-ascend` build works, including the daily packages.

```bash
# 1. Enable the capture (TritonParse installs it into the Ascend backend)
export TRITONPARSE_ENABLE_NPUIR_PASS_DUMP="1"

# 2. Run your Ascend kernel as usual
python my_kernel.py

# 3. Parse the trace
tritonparse parse ./logs --out ./parsed_output
```

If your kernel script uses `tritonparse.structured_logging.init()` explicitly,
setting the environment variable before `init()` is all that is needed — the
hook is installed there. Importing `tritonparse` without calling `init()` does
not install it, because `init()` is what also installs the compilation listener
that writes the trace.

A ready-to-run example that does all of this on a real device ships in the
package as
[`tritonparse.tools.ascend_npuir_capture`](../tritonparse/tools/ascend_npuir_capture.py):

```bash
python -m tritonparse.tools.ascend_npuir_capture --check   # diagnose the setup
python -m tritonparse.tools.ascend_npuir_capture --out ./npuir_demo
python -m tritonparse.tools.ascend_npuir_capture --filter hivm-graph-sync-solver,hivm-inject-sync
```

`--check` reports which of the required pieces is missing. Note in particular
that TritonParse traces compilations through `knobs.compilation.listener`, so a
triton-ascend build without `triton/knobs.py` (the 3.2 lineage) writes no trace
at all — not just no NPUIR passes.

Then open the parsed trace in the web UI and pick any `NPUIR Pass: …` entry from
the left/right panel selectors.

### Narrowing the dump

A full dump is ~100+ passes and ~1.5 MB of IR text per kernel. If you already
know which pass you care about, name it:

```bash
export TRITONPARSE_ENABLE_NPUIR_PASS_DUMP="1"
export TRITONPARSE_NPUIR_PASS_FILTER="hivm-graph-sync-solver,hivm-inject-sync"
```

Pass arguments are the tokens in parentheses in bishengir's dump headers:

```
// -----// IR Dump After GraphSyncSolver (hivm-graph-sync-solver) //----- //
                                ^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^
                                MLIR pass class   pass argument (use this)
```

## 🔧 How It Works

**No patched triton-ascend is required.** `tritonparse.structured_logging.init()`
installs the capture into the stock Ascend backend at runtime, so a plain
`pip install triton-ascend` (or a daily package) is enough.

| Step | Where | What happens |
|------|-------|--------------|
| 1 | `tritonparse/ascend_npuir.py` | Wraps the Ascend backend's `linalg_to_bin_enable_npu_compile_*` entry points and proxies the module-level `subprocess` name in `triton/backends/ascend/compiler.py` |
| 2 | same | The proxy rewrites the `bishengir-compile` command line (`--mlir-print-ir-after-failure` → `--mlir-print-ir-after-all --mlir-print-debuginfo`) and captures the subprocess output |
| 3 | same | Writes the combined stdout+stderr to `npuir_passes.log` in Triton's dump directory and records the path in the compilation metadata (`npuir_passes_log_path`) |
| 4 | `tritonparse/structured_logging.py` | Embeds that file into the trace as `kernel.npuir_passes.log` |
| 5 | `tritonparse/parse/trace_processor.py` | Splits the stream on the dump headers into one artifact per pass, and registers a stage for each |
| 6 | `tritonparse/backend.py` | Provides the stage descriptors (`NPUIR Pass: <label>`), display order, and label table |
| 7 | web UI | Renders the new stages; no frontend changes were needed |

The hook is installed only when `TRITONPARSE_ENABLE_NPUIR_PASS_DUMP` is set, only
if the Ascend backend is importable, and only once per process. It touches the
Ascend compiler's own `subprocess` name binding, never the global `subprocess`
module, so no other subprocess call in the process is affected. With the feature
off, nothing is installed and the compilation path is byte-for-byte unchanged.

Four design points worth knowing:

* **The standard MLIR flag is used**, not bishengir's own
  `--bishengir-print-ir-after=`, which is restricted to a small whitelist of
  passes. `--mlir-print-ir-after-all` has no such restriction.
* **`--mlir-print-debuginfo` is required**, or no dump carries `loc(...)`.
  MLIR stores locations on every op but only prints them when
  `OpPrintingFlags::printDebugInfo` is set, and it defaults to off. Without this
  flag every pass artifact is loc-free, so no pass maps back to a source line —
  which is most of the point of capturing the passes at all.
* **`--mlir-print-ir-after-failure` is replaced while dumping.** MLIR gates every
  after-pass print on "did the pass fail?" once that flag is present, which
  silences `--mlir-print-ir-after-all` as well. Since `--mlir-print-ir-after-all`
  prints after *every* pass, the failing pass's IR is still captured.
* **The dump is recorded under the kernel hash** in Triton's dump directory, and
  its path goes into the compilation metadata. That makes the trace
  self-contained: parsing works on a different machine, and a cache hit still
  carries the dump.

### Optional: in-tree triton-ascend patch

An equivalent patch for `triton/backends/ascend/compiler.py` is kept in
`design/patches/0001-triton-ascend-npuir-pass-dump.patch`. It is **not needed** —
use it only if you are upstreaming the change into triton-ascend. The two are
safe together: the runtime hook detects the flags are already present and does
not duplicate them.

## 📁 Artifact Naming

Each pass becomes an artifact named `kernel.<stage_name>`, where `stage_name` is
`npuir_pass_<sanitized pass argument>`:

| Pass argument | Stage name | Trace artifact |
|---------------|-----------|----------------|
| `convert-linalg-to-hfusion` | `npuir_pass_convert_linalg_to_hfusion` | `kernel.npuir_pass_convert_linalg_to_hfusion` |
| `hivm-graph-sync-solver` | `npuir_pass_hivm_graph_sync_solver` | `kernel.npuir_pass_hivm_graph_sync_solver` |

Passes that run more than once get a numeric suffix, in execution order:
`npuir_pass_cse`, `npuir_pass_cse_2`, `npuir_pass_cse_3`, …

> 💡 **Why no `.mlir` suffix?** The web UI recovers a stage name from a filename
> with `filename.split(".").pop()`. A trailing `.mlir` would collapse every pass
> artifact to the name `mlir` and silently drop both source mappings and MLIR
> syntax highlighting. `.ttadapter` and `.bcmlir` follow the same convention.

The raw combined stream is **not** kept as a selectable artifact; it is consumed
during parsing. A compact summary of what was captured is recorded in
`payload.npuir_passes`.

## 🧭 Using It in the UI

* **Panel selectors** list every stage, including all `NPUIR Pass: …` entries,
  sorted by pass execution order.
* **Default panels** stay on `TTIR` / `TTAdapter` — the pass stages are flagged
  `is_pass_level` in `ir_stages` and excluded from the default-panel and
  grouping-anchor heuristics, which would otherwise be swamped by 100+ entries.
* **Source mapping** works for essentially every pass. The dumps are captured
  with `--mlir-print-debuginfo`, without which MLIR prints no `loc(…)` at all
  and **no** pass can be tied back to a source line. In practice ~390 of ~400
  passes map back to the originating Python lines, which is what makes
  click-through from a pass to the kernel source work.

> ⚠️ **If source mapping looks empty**, `--mlir-print-debuginfo` is missing from
> the `bishengir-compile` command line. TritonParse adds it automatically; a
> patched triton-ascend that supplies its own dump flags must add it too. The
> demo and the on-device example both print a `mapped to source: N/M passes`
> line so this is visible at a glance.

## 🐛 Debugging Recipes

**Synchronization bugs** — compare the two sync passes side by side:

```bash
export TRITONPARSE_ENABLE_NPUIR_PASS_DUMP="1"
export TRITONPARSE_NPUIR_PASS_FILTER="hivm-graph-sync-solver,hivm-inject-sync"
```

**Kernel splitting** — capture `hivm-split-mix-kernel` and everything after it to
see how a mixed cube/vector kernel is partitioned.

**Lowering failures** — because the dump includes every pass up to the failure,
the last artifact in the trace is the IR as it looked when the failing pass ran.

## 📊 Cost

| Configuration | Artifacts | Raw size | Gzipped |
|--------------|-----------|----------|---------|
| Baseline | 5 | ~120 KB | — |
| + full NPUIR dump | ~400 | ~2.6 MB | ~55 KB |

`--mlir-print-debuginfo` accounts for most of the raw growth (1.5 MB → 2.6 MB)
but compresses away almost entirely: the added text is highly repetitive
`loc(...)` strings. Without it the dumps have no locations and no pass maps to a
source line, so it is not worth trading away.

Compilation time increases by roughly 10-20%. Parsing is linear in the amount of
IR, so a filtered dump is proportionally cheaper.

## 🧪 Verifying the Setup

```bash
# The toolchain must accept the flag and emit dumps
bishengir-compile kernel.ttadapter --mlir-print-ir-after-all -o /tmp/k \
  2>&1 | grep -c "IR Dump After"
```

If that prints `0`, your bishengir build does not support the standard MLIR
printing flags and the feature cannot work; check the toolchain version.

TritonParse ships an offline integration test that does exactly this check
against a checked-in TTAdapter fixture:

```bash
python -m unittest tests.cpu.test_npuir_bishengir_integration
```

It is skipped automatically when `bishengir-compile` is not on `PATH`.

There is also a runnable end-to-end demo that drives a real
`bishengir-compile`, builds the compilation trace event, and parses it with the
real `tritonparse parse` CLI:

```bash
export PATH=/path/to/bishengir/bin:$PATH
python -m tritonparse.tools.demo_npuir_pass_capture --out /tmp/npuir_demo
```

## 🖥️ Running on a Remote Ascend Server

Typical setup: a headless server with CANN, NPU and `triton-distributed-ascend`
(which vendors its own `triton-ascend`), and no browser. The NPUIR hook works
with the vendored `triton-ascend` too — it patches whichever
`triton.backends.ascend.compiler` module gets imported, standalone or vendored.

### 1. Install TritonParse on the server

```bash
# Into the same environment that runs your kernels (so triton/torch are present)
pip install "git+https://github.com/ltzone/tritonparse.git@npuir-parse"

# or, from a checkout
git clone -b npuir-parse https://github.com/ltzone/tritonparse.git
pip install -e ./tritonparse
```

Verify:

```bash
python -c "import tritonparse, triton; print(tritonparse.__file__); print(triton.__file__)"
```

The second path tells you which `triton` the hook will patch.

### 2. Run your workload with capture on

```bash
export TRITONPARSE_ENABLE_NPUIR_PASS_DUMP=1
# Optional: only the passes you care about, to keep the trace small
export TRITONPARSE_NPUIR_PASS_FILTER="hivm-graph-sync-solver,hivm-inject-sync"
export TRITON_TRACE="./logs"

python your_kernel_or_test.py
```

If you just want to confirm the pipeline end to end before wiring it into your own
workload, the shipped example is a complete workload:

```bash
python -m tritonparse.tools.ascend_npuir_capture --out ./npuir_demo
```

You should see one line from TritonParse confirming the hook is in:

```
... - tritonparse - INFO - Ascend NPUIR pass dump enabled (filter: hivm-graph-sync-solver,hivm-inject-sync)
```

If that line is missing, the Ascend backend was not importable when
`tritonparse.structured_logging.init()` ran, and no passes will be captured.

> 💡 **Distributed runs**: set the variables in the environment of every rank, and
> give each rank its own trace folder (`TRITON_TRACE=./logs_rank$RANK`) or use
> `--all-ranks` at parse time. The dump is per-kernel and per-process, so ranks
> do not interfere.

### 3. Parse on the server

Parsing needs the IR artifacts, which live on the server, so run it there:

```bash
python -m tritonparse parse ./logs --out ./parsed_output
```

### 4. View it

The web UI is fully client-side, so pick whichever is convenient.

**Option A — port-forward (live, no copying).** Serve the parsed directory and
forward the port to your laptop:

```bash
cd parsed_output && python -m http.server 8000
# from your laptop:
ssh -N -L 8000:localhost:8000 user@server
```

Then open
`http://localhost:8000/standalone.html?json_url=http://localhost:8000/<trace>.ndjson.gz`.

> ⚠️ If `http://localhost` does not load on the server, check `no_proxy`. A
> corporate proxy can intercept localhost requests and return `401`.

**Option B — copy the trace to your laptop.** The trace is self-contained, so a
plain `scp` of the parsed `.ndjson.gz` is enough:

```bash
scp user@server:~/parsed_output/*.ndjson.gz .
```

Then open <https://meta-pytorch.org/tritonparse/> and drop the file in, or use
the standalone build from `npm run build:single` in `website/`.

> 💡 Use `TRITON_TRACE_COMPRESSION=gzip` if the traces are large; the NPUIR dump
> compresses roughly 35:1 (1.5 MB of IR per kernel becomes ~40 KB).

### 5. Check the capture worked

The fastest check is to count the pass stages in the parsed trace:

```bash
python - <<'PY'
import gzip, json, glob

path = glob.glob("./parsed_output/*.ndjson.gz")[0]
with gzip.open(path, "rt") as f:
    for line in f:
        event = json.loads(line)
        if event.get("event_type") == "compilation":
            stages = event["payload"].get("ir_stages", [])
            passes = [s for s in stages if s["name"].startswith("npuir_pass_")]
            print(f"{len(passes)} NPUIR pass stages")
            for s in passes[:5]:
                print(f"  {s['display_order']:>5}  {s['display_name']}")
            break
PY
```

With the default settings and a real kernel this prints ~400 stages. A count of
zero means the dump was never produced — check step 2's confirmation line.

To list kernel launches instead (needs `TRITON_TRACE_LAUNCH=1`), point `info` at
the **raw** log, not the parsed output:

```bash
python -m tritonparse info ./logs/*.ndjson --kernel <name>
```

## 🔁 Upgrading / Reinstalling

TritonParse is a pure-Python package, so no rebuild is needed. What matters is
that the *environment that runs the kernel* gets the new code — the hook lives
in `tritonparse/ascend_npuir.py` and is imported by `tritonparse.structured_logging`.

```bash
# In the env that runs the kernel (not a separate analysis env)
pip uninstall -y tritonparse
pip install "git+https://github.com/ltzone/tritonparse.git@npuir-parse"

# or, from a checkout
git -C /path/to/tritonparse pull
pip install -e /path/to/tritonparse
```

Nothing to recompile: there is no build step, no extension module, and the
frontend is only needed for viewing.

### Confirm the upgrade actually landed

The single check that matters is whether the injected flags include
`--mlir-print-debuginfo`. Without it, no pass maps back to a source line.

```bash
python -c "
from tritonparse.ascend_npuir import _rewrite_cmd
f = _rewrite_cmd(['/x/bishengir-compile', 'in.mlir', '-o', 'out'])
print(f)
print('debuginfo:', 'YES' if '--mlir-print-debuginfo' in f else 'NO  <-- old version')
"
```

If it prints `NO`, a stale install is shadowing the new one. Check with:

```bash
python -c "import tritonparse; print(tritonparse.__file__)"
pip show tritonparse | grep -E "Version|Location"
```

### Which file is 122 KB?

Three different artifacts get confused, and only the last one reflects whether
locations were captured:

| Artifact | Path | Size (this fixture kernel) |
|----------|------|---------------------------|
| bishengir dump | `<TRITON_DUMP_DIR>/<hash>/npuir_passes.log` | 1.5 MB without loc, **2.7 MB** with |
| raw trace | `<TRITON_TRACE>/*.ndjson` | 2.8 MB (uncompressed) |
| **parsed trace** | `<out>/*_mapped.ndjson.gz` | **43 KB without loc, ~125 KB with** |

So a `*_mapped.ndjson.gz` of ~122 KB is the *expected* size once locations are
being captured; the loc-free one is ~43 KB. The demo prints all three sizes
labelled at the end for exactly this reason.

The authoritative check is not the size but the mapping rate:

```bash
python -m tritonparse.tools.ascend_npuir_capture --check   # then run without --check
# look for:  mapped to source: N/M passes   (expect ~98%)
```

## 🩺 Diagnosing "no loc in the UI"

Several unrelated problems present identically in the UI, so there is a tool
that tells them apart from a trace alone:

```bash
python -m tritonparse.tools.check_npuir_trace ./parsed/*.ndjson.gz
```

```
  NPUIR pass artifacts      : 398
    IR contains loc(...)    : 398  (expect ~all)
    has source_mappings     : 391  (expect ~all)
  source_mappings top keys  : 393  (expect ~401)
  sample: npuir_pass_canonicalize_module
    IR line -> /path/to/kernel.py:38:0

  VERDICT: locations captured and mapped.
```

It also prints the upstream artifacts, because bishengir can only print the
locations its *input* still carries:

```
  upstream IR (bishengir's input is ttadapter/bcmlir):
    add_kernel.bcmlir            loc(...) = 0
    add_kernel.ttadapter         loc(...) = 0
    add_kernel.ttir              loc(...) = 53
```

It distinguishes the cases that otherwise look the same:

| Verdict | Meaning | Fix |
|---------|---------|-----|
| locations captured and mapped | working | — |
| no locations, ttir/ttadapter both fine | the dump lacks `--mlir-print-debuginfo` | upgrade TritonParse, regenerate |
| **no locations, ttir has them but ttadapter/bcmlir do not** | the triton-ascend lowering dropped them before bishengir ran | report to triton-ascend; no dump flag can help. Use `ttir` for source correlation meanwhile |
| locations present but not mapped, `loc(...)` reaches a `.py` | TritonParse parsing bug | report it with the trace |
| locations present but only parse positions | same upstream loss, seen with the flag on | as above |

> ⚠️ **Parse positions are not source locations.** MLIR's parser stamps every op
> it reads with a position in the file being parsed, so a dump of a module whose
> real locations were stripped upstream still contains `loc(...)` — all pointing
> at the temporary `kernel.mlir` triton-ascend writes and deletes. TritonParse
> drops those mappings rather than pointing you at a file that no longer exists;
> a mapping is kept only if it reaches a `.py` file.

A quick hand check for the middle case: count the real locations in the dump.

```bash
grep -c 'loc("' "$TRITON_DUMP_DIR"/*/npuir_passes.log   # ~7k, not 0 or 3
```

Note that `grep -c 'loc('` (without the quote) is misleading: `memref.alloc(`
matches it. And a loc-free dump still contains a handful of `loc("...")` from
bishengir's *error messages*, so "a few" also means broken.

## ❓ Troubleshooting

| Symptom | Likely cause |
|---------|--------------|
| No `NPUIR Pass: …` stages in the trace | `TRITONPARSE_ENABLE_NPUIR_PASS_DUMP` was not set in the process that ran the kernel (not just the parse step), or `tritonparse.structured_logging.init()` was never called |
| A one-line warning `Ascend NPUIR pass dump enabled` is absent from the run | The Ascend backend was not importable, or `init()` had not been called yet when the env var was set |
| Dump file exists but trace has no passes | The trace was written before the dump path was recorded; re-run with the variable set |
| Only a handful of passes captured | `TRITONPARSE_NPUIR_PASS_FILTER` is set |
| `Unknown command line argument '--mlir-print-ir-after-all'` from bishengir | The toolchain predates the standard MLIR printing flags; the feature cannot work on it |
| Trace is very large | Use `TRITONPARSE_NPUIR_PASS_FILTER`, or `TRITON_TRACE_COMPRESSION="gzip"` |
